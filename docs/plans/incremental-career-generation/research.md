# リサーチ: 動的キャリア生成の差分更新（ブレ防止 + インクリメンタル更新）

調査日: 2026-03-08
調査タイプ: 複合

## 調査ゴール
毎回ゼロから LLM で生成する現在のフローを改善し、前回結果を保存して差分のみ更新するフローの設計パターンを明らかにする。

## 現状

### 生成フロー
1. `generate-site.sh` が `dist/index.html` を毎回テンプレートから上書き生成（`<!-- DYNAMIC_CAREER:会社名 -->` プレースホルダー挿入）
2. Claude Code Action が SKILL.md の指示に従い、プレースホルダーを HTML に置換（毎回ゼロから分析・生成）
3. Cloudflare Pages にデプロイ

### 問題点
- **前回生成結果はどこにも保存されない**（dist/ は .gitignore、ワークフロー終了で揮発）
- 同じ入力データでも毎回異なる出力が生成される（LLM の非決定性）
- PR データに変化がなくても毎回 Claude を呼び出す（コスト非効率）

## 調査結果

### 方式の比較

| 観点 | 方式A: 前回HTML保存 + アンカー | 方式B: 中間JSON分離 | ハッシュスキップ |
|------|-------------------------------|-------------------|----------------|
| 複雑さ | 低〜中 | 高 | 低 |
| ブレ防止 | 7.4倍削減（研究報告） | 分類は決定的、文章のみブレ | ー（スキップ時は完全一致） |
| コスト削減 | 入力増だがCache可 | API呼び出し2倍 | スキップ時ゼロ |
| 実装変更 | SKILL.md + ワークフロー | SKILL.md大幅改修 | ワークフローのみ |

### 推奨: 段階的導入（ハッシュスキップ → 方式A）

**Phase 1: 入力ハッシュによる LLM 呼び出しスキップ**（複雑さ: 低 / 効果: 高）
- `my_merged_prs` の SHA-256 ハッシュを R2 に保存
- 前回ハッシュと一致 → Claude 呼び出しスキップ、前回 HTML をそのまま使用
- PR マージがなかった週は API 費用ゼロ
- Bash のみで実現可能（Claude Code Action の前にシェルスクリプトで判定）

**Phase 2: 前回出力HTMLをアンカーとして渡す（方式A）**（複雑さ: 中 / 効果: 中〜高）
- 入力データに変化があった場合のみ実行
- 「前回の出力 HTML を維持し、新規データの分だけ更新してください」という指示でブレを抑制
- 前回 HTML を R2 に保存（会社ごとの HTML フラグメント）
- SKILL.md に「前回結果がある場合は差分更新モードで動作する」指示を追加

### 保存すべきデータ

| データ | 保存先 | 用途 |
|--------|--------|------|
| 会社ごとの生成済み HTML フラグメント | R2 (`884js-data/career-html/{会社名}.html`) | Phase 1: スキップ時の再利用 / Phase 2: アンカー |
| 入力データハッシュ | R2 (`884js-data/career-hash/{会社名}.sha256`) | スキップ判定 |

### ブレ防止の知見
- temperature=0 でも完全な決定性は保証されない（GPU並列処理の丸め誤差等）
- 前回出力をアンカーとしてプロンプトに含めるのが最も効果的（7.4倍のブレ削減）
- 出力の構造（HTMLクラス名・属性）を厳密に指定するとドリフトを抑制できる

## 推奨・結論

**Phase 1（ハッシュスキップ）から始める**のが最もコスパが良い。PR マージがない週のClaude呼び出しを完全にスキップでき、実装はワークフローのシェルスクリプト追加のみ。

Phase 2（アンカー方式）は Phase 1 の基盤（R2 への HTML 保存）の上に追加できるため、段階的に導入可能。
